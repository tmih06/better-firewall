# What makes bfw faster: a measured comparison with UFW

**Status: measured study.** The numbers here come from the committed hosted-CI
snapshots in `scripts/charts/testdata/` and the generated benchmark document
`docs/benchmarks.md`. Nothing in this report is a projection or a local
best-case run.

The short version:

* **Setup is 8–32× faster.** At 1,000 rules, adding the rules and enabling the
  firewall took **8.6695 s with bfw** and **156.3283 s with UFW** — an **18.0×**
  difference.
* **Almost all of that difference is per-rule CLI work, not the kernel apply.**
  At 1,000 rules, rule addition accounted for **99.7%** of the 147.7 s gap. The
  enable step itself was 61.9 ms for bfw and 497.8 ms for UFW (8.0×).
* **Packet throughput is not better, and no traffic cost was measured.** Across
  the run, bfw and UFW served **28,565,533 requests with zero errors and zero
  dropped iterations**. The largest p95 latency deviation from the no-firewall
  container was **7.1%**, and the deviations fall on both sides of zero.
* **Memory is the resource where bfw wins at scale.** At 1,000 rules it used
  **14% less mean resident memory** than UFW. CPU is a tie.
* **Protection adds a capability UFW does not have.** The current ban-set
  compiler handles 10,000 bans in **1.255 ms** with 115 allocations, and the
  attack lab shows an SSH brute-forcer banned **0.1 s** after the fifth failed
  login and a CrowdSec LAPI ban applied **0.9 s** after it was pushed.

The accurate claim is therefore:

> bfw configures and applies a ruleset roughly 8–32× faster than UFW in this
> workload, uses less memory as the ruleset grows, and keeps packet latency at
> the no-firewall noise floor. Its dynamic-ban path is an operational advantage;
> it is not a packet-forwarding speed advantage.

That distinction matters. Both programs are management frontends over the Linux
netfilter data path. The benchmark measures the cost of expressing and applying
policy, and the cost of the resulting ruleset under traffic — not a different
kernel packet filter.

## 1. What was compared

| Item | Value |
|---|---|
| Firewall managers | bfw 0.1.0, UFW 0.36.2 |
| Host kernel | Linux 6.17.0-1022-azure, x86_64 |
| Load generator | k6 v2.3.0, 10 VUs, 50 peak VUs |
| Traffic duration | 10 s per run, 2 s warm-up, 3 repeats |
| Rule counts | 10, 100, 500, 1,000 |
| Profiles | keep-alive, connection churn, mixed payload |
| Containers | separate `server` and `attacker` containers on an internal-only Docker network |
| Privileges | only `NET_ADMIN`; no published host ports; `no-new-privileges` |
| Data source | [`summary.json`](../scripts/charts/testdata/summary.json), `protection-benchmarks.txt`, `attack-summary.json` |

UFW is the default firewall management layer on Ubuntu, so it is the natural
baseline. bfw deliberately reproduces UFW's CLI, output, and exit-code behavior
where practical. The comparison is about two implementations of the same
administrative contract.

Both programs ultimately install netfilter rules. bfw talks nftables through
the native netlink API. UFW drives iptables. The benchmark image installs both
iptables and nftables, but the snapshot does not record which iptables backend
UFW used. This report therefore does not claim a kernel-datapath difference; it
compares the management paths and the resulting rulesets.

## 2. Method

### 2.1 Rule-setup timing

`scripts/perf/apply_rules.py` starts each firewall CLI as a child process and
measures wall-clock time externally. Setup is split into two phases:

1. **Rule add** — set the default incoming policy, add the requested number of
   single-port allow rules, then add the HTTP allow rule.
2. **Enable** — run the engine's enable command once.

The split matters because the two phases have very different costs and scaling
behavior.

The benchmark resets the firewalls before each measurement, so the rule-add
phase starts from a disabled firewall. Both engines must still parse and persist
their state on every CLI invocation. The enable phase is where the ruleset is
actually installed.

Three repeats are run per cardinality. The report uses the recorded means.
`scripts/perf/run.sh` alternates which engine goes first on successive repeats
to reduce ordering bias.

### 2.2 Packet-path timing

For each repeat and profile, k6 drives HTTP traffic through the defended
container. The no-firewall baseline is measured at the same cardinality and in
the same repeat as the bfw/UFW pair.

The harness verifies semantic equivalence before trusting a run:

* with no firewall, both the permitted port 8080 and the denied port 8081 are
  reachable;
* after bfw or UFW is enabled, 8080 is reachable and 8081 is not;
* all 24 engine/cardinality/repeat rulesets pass both controls.

A throughput number without those controls would only prove that some rules
were installed, not that they implemented the intended policy.

### 2.3 Resource sampling

Resource samples are taken once per second from the defender container, giving
24 samples per engine in the 1,000-rule mixed scenario. The memory and CPU
tables in this report use the mean over three repeats and three traffic
profiles, matching the generated resource chart. “Mean resident memory” is the
container's sampled RSS; “CPU overhead” is percentage points above the
no-firewall container measured in the same cell.

### 2.4 Protection microbenchmarks

The protection numbers come from Go benchmarks in the `protection-benchmarks`
CI job, recorded as one sample per case. They cover:

* parsing and observing one failed-login journal event;
* decoding a CrowdSec decision batch;
* compiling the nftables threat-ban set at 100, 1,000, and 10,000 bans;
* compiling and rendering normal and limit-rule rulesets.

These are configuration-path measurements. They do not include journal I/O,
CrowdSec network latency, netlink apply time, or packet processing.

### 2.5 Attack lab

The attack results come from a separate hosted job. It drives nmap recon,
hping3 SYN floods, a TCP connect flood, 12 SSH brute-force attempts, and
CrowdSec-compatible LAPI ban/unban pushes at a container with 10 allow rules,
for 6 s per attack. The attack lab is evidence about behavior under attack, not
a packet-throughput benchmark.

### 2.6 What “mean” means here

`scripts/perf/compare.py` averages throughput and latency across the three
repeats. The report does not have confidence intervals or a formal significance
test. That is a limitation, not a hidden correction: the packet-path
differences are small enough that the correct conclusion is “no demonstrated
difference,” not “bfw is 1% faster” or “UFW is 1% faster.”

## 3. Findings

### 3.1 The headline: setup is 8–32× faster

| Rules | bfw rule add | UFW rule add | bfw enable | UFW enable | bfw total | UFW total | Total speed-up |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 10 | 0.0389 s | 1.1605 s | 0.0116 s | 0.4435 s | 0.0505 s | 1.6041 s | **31.8×** |
| 100 | 0.3791 s | 9.2237 s | 0.0136 s | 0.3983 s | 0.3927 s | 9.6219 s | **24.5×** |
| 500 | 3.1815 s | 62.1783 s | 0.0389 s | 0.4424 s | 3.2203 s | 62.6207 s | **19.4×** |
| 1,000 | 8.6076 s | 155.8305 s | 0.0619 s | 0.4978 s | 8.6695 s | 156.3283 s | **18.0×** |

Derived per-rule cost:

| Rules | bfw add per rule | UFW add per rule | Rule-add speed-up |
|---:|---:|---:|---:|
| 10 | 3.89 ms | 116.05 ms | 29.8× |
| 100 | 3.79 ms | 92.24 ms | 24.3× |
| 500 | 6.36 ms | 124.36 ms | 19.5× |
| 1,000 | 8.61 ms | 155.83 ms | 18.1× |

The total speed-up falls as the rule count rises, but the absolute advantage
grows enormously: 1.55 s at 10 rules, 9.23 s at 100, 59.40 s at 500, and
147.66 s at 1,000. The ratio falls because both engines' per-command cost grows
with the size of the stored ruleset, and the fixed portion is a larger share at
small rule counts.

At 1,000 rules, bfw's per-add cost is about 8.6 ms. That is consistent with a
native Go process loading, modifying, and writing a compact JSON state file.
UFW's per-add cost is about 156 ms, roughly 18× higher. The harness does not
trace inside UFW, so this report treats the Python-frontend/whole-ruleset
rewrite explanation as the architectural reason for the gap, not as a measured
syscall attribution.

### 3.2 Where the gap actually comes from

The setup total is `rule add + enable`, so the gap decomposes exactly:

| Rules | Total gap | From rule add | From enable | Rule-add share |
|---:|---:|---:|---:|---:|
| 10 | 1.554 s | 1.122 s | 0.432 s | 72.2% |
| 100 | 9.229 s | 8.845 s | 0.385 s | 95.8% |
| 500 | 59.400 s | 58.997 s | 0.404 s | 99.3% |
| 1,000 | 147.659 s | 147.223 s | 0.436 s | **99.7%** |

Two things stand out:

1. **Rule addition dominates at scale.** At 1,000 rules it accounts for 99.7%
   of the 147.7 s difference. Optimizing the nftables apply alone cannot explain
   the headline number.
2. **The enable gap is roughly constant at 0.38–0.44 s.** UFW's enable phase
   costs 0.40–0.50 s in this range; bfw's costs 12–62 ms. Even at 1,000 rules,
   bfw's faster apply saves about 0.44 s. It is real, but it is not where most of
   the 18× comes from.

The compile microbenchmark makes the same point independently. At 1,000 rules,
the current ruleset compiler takes **137.61 µs** and 92 allocations. That is
0.14 ms of the 8.67 s setup time. Even if compilation were free, the setup gap
would remain dominated by the repeated CLI/state work.

### 3.3 Why rule addition is cheap for bfw

bfw separates policy mutation from kernel application:

* `internal/cli/commands_rules.go:commitState` saves the mutated state.
* `internal/cli/commands_rules.go:live` returns true only when the firewall is
  enabled and the command is not a dry run.
* When the firewall is disabled, adding a rule takes the state-only path: load
  JSON, mutate the in-memory rule list, save it.
* `internal/store/store.go:Save` writes the compact state atomically (temporary
  file plus rename), so a failed write does not leave a half-written
  `rules.json`.
* `enable` then loads the complete state once and calls the backend.

The UFW-compatible CLI contract still requires one process per rule, so bfw pays
process startup, JSON parsing, and full-file rewriting on every add. That is why
per-add cost is milliseconds rather than microseconds. UFW pays a larger
per-process cost, and its rule-command time grows with the ruleset as well.

The store has been specifically optimized for this pattern:

* `4a4d516` writes `rules.json` compact instead of indented. The commit measured
  1,000 sequential adds at **15.28 s → 11.00 s (−28%)** and the file at
  **670 KB → 320 KB (−52%)**.
* `4790726` counts the rule arrays before decoding and pre-sizes the slices.
  The commit measured a 1,000-rule `Load` at **1,239,822 B → 443,018 B (−64%)**,
  removing repeated `reflect.growslice` work.

Those are direct improvements to the dominant phase. They do not make the
headline claim all by themselves, but they explain why bfw's per-add cost is as
low as it is.

### 3.4 The enable path: compile once, apply one batch

`internal/backend/nft/apply.go:Apply` does the following:

1. compile the complete state into nftables objects;
2. open one netlink connection with 8 MiB read and write buffers;
3. list existing tables and delete only the managed tables that actually
   exist;
4. add the managed table, NAT tables, chains, sets, set elements, and rules to
   the connection;
5. commit everything with a single `Flush()`.

The single batch is an atomic replacement: if compilation or any pre-flush step
fails, the kernel ruleset is not partially updated. The table deletion step is
conditional because deleting a table that does not exist would fail the whole
batch.

This is the part that most directly resembles bfw's “one transaction” design,
and it is measurably faster than UFW's enable step: **61.9 ms versus 497.8 ms**
at 1,000 rules (8.0×). But because the enable step is a small fraction of total
setup time, this is a **secondary** contributor to the headline speed-up.

Fragments and sysctl handling are outside this path. If `before`/`after`
fragment files exist, `applyRuleset` applies them in a second transaction with
an `nft -c` check; a failure flushes the core ruleset. The benchmark's normal
ruleset does not use fragments, so fragment cost is not part of the recorded
setup numbers.

### 3.5 Packet path: no measurable cost, no advantage

Across the entire comparison run:

| Measure | Result |
|---|---:|
| Requests served | 28,565,533 |
| Request errors | 0 |
| Dropped iterations | 0 |
| Response checks passed | 28,565,489 |
| Largest p95 deviation from no firewall | 7.1% |

At the 1,000-rule mixed profile:

| Scenario | Throughput (req/s) | p95 latency (ms) |
|---|---:|---:|
| No firewall | 17,745.37 | 4.066 |
| bfw | 17,503.05 | 4.082 |
| UFW | 17,546.12 | 4.117 |

Across all twelve rule-count/profile comparisons, the raw bfw/UFW throughput
ratio ranged from **0.972× to 1.002×** (mean 0.994), and the raw p95 ratio from
**0.969× to 1.040×** (mean 1.001). The generated chart deliberately does not
plot those ratios. Instead it plots each engine's p95 deviation from the
no-firewall container, because the ratios put three near-identical values in
every cell and invite the reader to hunt for a winner that the data does not
contain.

The no-firewall control moves by a similar amount: bfw is faster than no
firewall in 6 of the 12 cells, UFW in 7, and the signs change with rule count.
A firewall cannot remove latency, so both signs are measurement noise. The
correct conclusion is **no demonstrated packet-path difference**, not a small
bfw win.

Why is there no large packet-path win? The benchmark's rules are single-port
allow rules. At 1,000 rules, both engines evaluate a long sequence of per-rule
matches; neither can turn that into a constant-time lookup without a set-based
ruleset. bfw's threat-ban sets and named-set support are not the dominant
structure in this workload. The result is what the architecture predicts:
similar netfilter work, similar throughput.

### 3.6 Resource use: less memory at scale, CPU tie

The resource chart uses the mean over three repeats and three traffic profiles.

| Rules | bfw memory (MiB) | UFW memory (MiB) | bfw vs UFW | bfw CPU overhead | UFW CPU overhead |
|---:|---:|---:|---:|---:|---:|
| 10 | 18.5 | 18.5 | level | +1.1 pp | +2.7 pp |
| 100 | 19.9 | 20.3 | −2% | +1.7 pp | +0.7 pp |
| 500 | 23.5 | 26.1 | −10% | −1.8 pp | +3.8 pp |
| 1,000 | 28.8 | 33.6 | **−14%** | −0.1 pp | −1.3 pp |

At 1,000 rules the memory saving is 14.0%, 13.9%, and 14.6% in the keep-alive,
churn, and mixed profiles individually. This is a real effect that grows with
ruleset size; it is not a fixed discount, and it is worth nothing on a small
ruleset.

CPU is a tie. Both engines sit within about two percentage points of running no
firewall at all, and bfw's figure changes sign between rule counts. Absolute CPU
is dominated by the traffic profile: churn runs at 10.9% and mixed at 76.9% for
the same 1,000-rule ruleset, because the load generator is the bottleneck in
both cases. The resource table is not evidence that either engine is faster on
CPU.

### 3.7 Protection path: cheap set compilation and dynamic bans

| Path | Work per operation | Time | B/op | Allocs/op | Throughput |
|---|---:|---:|---:|---:|---:|
| Journal failure detector | 1 failed-login event | 0.879 µs | 122 | 2 | — |
| CrowdSec JSON decode | 100 decisions | 56.63 µs | 26,085 | 119 | 217.3 MB/s |
| nft ban-set compile | 100 bans | 29.28 µs | 90.2 kB | 91 | — |
| nft ban-set compile | 1,000 bans | 128.12 µs | 381.1 kB | 93 | — |
| nft ban-set compile | 10,000 bans | 1.255 ms | 3.19 MB | 115 | — |

The apparent per-ban cost is now nearly flat at scale:

| Bans | Apparent time per ban | Bytes per ban | Allocations per ban |
|---:|---:|---:|---:|
| 100 | 293 ns | 902 B | 0.91 |
| 1,000 | 128 ns | 381 B | 0.09 |
| 10,000 | 126 ns | 334 B | 0.01 |

At 100 bans the fixed compiler overhead is visible; by 1,000 bans the set work
dominates, and 10,000 bans cost about 126 ns per ban to compile. The current
10,000-ban case is **1.255 ms with 115 allocations**. The optimization commit
`d7d1b74` recorded the same path dropping from **60,088 to 114 allocations**
with about **−48% time**, which is the controlled evidence behind the current
shape.

The design reason is in `internal/backend/nft/compile.go`:

* `compileThreatBans` turns active bans into IPv4 and IPv6 interval sets
  (`bfw_threat_bans`, `bfw_threat_bans6`).
* `compileAddressSet` merges overlapping and adjacent intervals before
  submitting them, because overlapping intervals make the kernel reject the
  whole batch.
* `addThreatBanRules` installs **one lookup rule per family** in the before
  input and forward chains, not one rule per banned address.
* The ban lookup is placed before the established/related accept rule, so a
  newly banned address is dropped even if conntrack already considers the flow
  established.
* `d7d1b74` moved limit sets, dynsets, and address interval keys into compile
  arenas and switched interval parsing to `netip`; its commit measured the
  10,000-ban compiler at **60,088 → 114 allocations** and about **−48% time**.
* `76680b6` caches shared expression literals; its commit measured the
  1,000-rule ruleset compile at about **90 allocations and 0.32 MB**.

That is the scalable part of the protection design: packet-path ban matching is
a set lookup whose cost does not grow with one rule per ban. It is also
different from the benchmark's 1,000 single-port rules, which remain a linear
rule chain.

One caveat: the microbenchmark measures compilation, not the full update
transaction. A live ban update also rewrites state and applies the ruleset. The
1.255 ms figure is therefore a lower bound on the protection update cost, not
the whole end-to-end path.

### 3.8 Attack lab: protection works under load

The attack job uses 10 allow rules and 6 s per attack. It is separate from the
packet-throughput comparison.

| Measure | No firewall | bfw | UFW |
|---|---:|---:|---:|
| nmap ports 1–2000 | 2,000 closed in 0.13 s | 1,999 filtered in 7.13 s | 1,999 filtered in 7.22 s |
| Ports visible in 8070–8110 | 8080, 8081 | 8080 only | 8080 only |
| Legit requests, SYN flood → denied | 163,056 | 145,646 | 154,074 |
| Legit requests, SYN flood → allowed | 148,100 | 145,602 | 145,164 |
| Legit requests, connect flood | 126,818 | 131,771 | 122,735 |
| Failed legitimate requests | 0 | 0 | 0 |
| SSH brute-force, 12 tries | attacker unbanned | **banned in 0.1 s, SSH blocked** | attacker unbanned |
| LAPI ban → attacker | — | **blocked in 0.9 s, unbanned in 0.1 s** | not supported |

Under either firewall, recon becomes seconds of filtered ports instead of
instant answers, and legitimate traffic survives every flood with no failures.
The per-attack request counts vary in both directions; the report does not use
them to crown a throughput winner.

The last two rows are the operational difference. UFW has no dynamic-ban
mechanism, while `bfw protect` banned the brute-forcer 0.1 s after the fifth
failed login and applied a LAPI decision 0.9 s after it was pushed, without
interrupting the legitimate stream.

The current ruleset-compile microbenchmark:

| Rules | Time | B/op | Allocs/op |
|---:|---:|---:|---:|
| 10 | 28.10 µs | 125.9 kB | 85 |

The 1,000-rule compile is **0.14 ms**, more than four orders of magnitude below

## 4. Mechanism map

| Mechanism | Where it lives | What the evidence supports | Size of effect |
|---|---|---|---|
| Native Go CLI; no Python startup | `cmd/bfw`, `internal/cli` | Per-rule add cost 3.8–8.6 ms vs UFW's 92–156 ms | **Dominant**; 99.7% of the 1,000-rule gap |
| State-only mutation while disabled | `commitState`, `live` | Rule adds do not touch the kernel until enable | Explains cheap repeated adds |
| Compact, pre-sized state I/O | `internal/store/store.go`; `4a4d516`, `4790726` | 1,000 adds −28%; 1,000-rule load −64% bytes | Directly reduces the dominant phase |
| Atomic persistence | `internal/store/store.go:Save` | Temp file + rename; no partial state | Correctness and safety |
| Compile once, one netlink batch | `internal/backend/nft/apply.go:Apply` | Enable 61.9 ms vs 497.8 ms at 1,000 rules | Real but secondary; 0.44 s of the 147.7 s gap |
| Conditional table deletion | `Apply` | Existing managed tables are deleted in the same batch; missing tables are skipped | Avoids a batch failure |
| 8 MiB netlink buffers | `Apply` socket options | Large full-ruleset batches can exceed default buffers and fail with `ENOBUFS` | Reliability/scalability |
| Expression caching and arenas | `compile.go`, `render.go`; `d7d1b74`, `76680b6`, and the optimization series | 1,000-rule compile 137.61 µs / 92 allocs; 10,000-ban compile 1.255 ms / 115 allocs | Large reduction from earlier alloc-heavy paths |
| Streaming/indexed rendering | `render.go`; `1d2df47`, `e251666`, `aa172ab`, `0d782f6` | 1,000-rule render 361.60 µs / 72 allocs | Keeps status/diff paths cheap |
| Threat-ban interval sets | `compileThreatBans`, `compileAddressSet` | One lookup rule per family; 10,000-ban compile 1.255 ms | Keeps ban matching independent of ban count |
| Bans before conntrack accept | `compileBefore` / `addThreatBanRules` | Banned flows are dropped even if already established | Security behavior |
| `inet` table for both families | `compile.go` | One managed table family; dual-stack rules in one chain model | Architectural simplification; not isolated here |

What is **not** supported by this study:

* that bfw forwards packets faster than UFW, or that nftables beats UFW's
  iptables path on this workload;
* that bfw uses less CPU than UFW;
* that named sets make the 1,000-rule single-port workload faster;
* that the compiler allocation work caused the headline setup gap;
* that UFW's whole 156 s is spent in one specific internal operation; the
  harness times the command, not the Python internals.

Two cautions about this table:

1. The commit-message measurements were taken on the developer's test setup,
   not necessarily the same run as the current snapshot. They show direction
   and magnitude, not a controlled before/after under one runner.
2. Some changes improve `status`/`diff` rendering rather than the setup path.
   They are included because they are part of the same allocation-reduction
   series and because the report uses the generated compile/render benchmarks.

The single largest setup lever remains the per-rule CLI/state path. The store
changes are therefore more important to the headline number than the nftables
compiler changes.

## 6. Threats to validity

1. **One hosted snapshot, three repeats, no confidence intervals.** Means are
   reported; a different runner, kernel, or noisy neighbour could move the
   packet-path numbers by more than the bfw/UFW gap.
2. **Single machine and kernel.** The setup ratios are large enough to be
   credible, but the absolute milliseconds are machine-specific.
3. **The workload is deliberately simple.** Single-port allow rules exercise
   linear rule chains, not set lookups. A 1,000-port set or a 10,000-address
   set could produce a different nftables/iptables result.
4. **Churn is capped at 200 req/s.** That profile cannot distinguish engines on
   throughput.
5. **Resource sampling is coarse.** One-second samples, 24 per engine, a shared
   container host, and means over three profiles.
6. **UFW internals are not traced.** The report attributes the per-command gap
   to the Python frontend and whole-ruleset persistence by architecture and by
   the measured scaling. A syscall or Python-profile trace would be needed to
   prove the internal split.
7. **Setup and packet path are separate experiments.** No run measures
   “configure while traffic is flowing,” so the interaction between rule
   updates and live traffic is not covered.
8. **Protection numbers are one sample per case.** They are useful for order of
   magnitude and for comparing ban counts, not for tight confidence bounds.
9. **Protection compile is not the whole update path.** The benchmark excludes
   netlink apply, state save, and CrowdSec network time.
10. **Attack-lab request counts are not a throughput benchmark.** They show
    availability under attack, not a statistically controlled comparison.

---

## 7. What to measure next

1. **Profile one `bfw allow` end to end.** Split process startup, JSON parse,
   rule insertion, JSON marshal, and write. The compact/pre-sized state work
   removed the largest terms; the remaining 8.6 ms at 1,000 rules is the next
   target.
2. **Split `enable` into compile, netlink flush, fragment apply, and
   persistence.** At 1,000 rules the compile is 0.14 ms and enable is 61.9 ms,
   so the split would show whether netlink, table listing, or process startup
   dominates.
3. **Add a set-based workload.** Compare one rule containing a 1,000-port or
   1,000-address set against 1,000 individual rules. That is the workload where
   nftables sets could produce a packet-path difference; the current benchmark
   cannot see it.
4. **Measure a live ban update end to end.** Include state save, compile,
   netlink apply, and the next packet's verdict. The current 1.255 ms is compile
   only.
5. **Increase repeats and report medians and intervals.** Three repeats are
   enough to catch gross regressions, not to resolve 1% packet-path
   differences.
6. **Instrument UFW.** A syscall trace or Python profile would turn the
   architectural explanation for the per-add gap into a measured one.

## 8. Reproduction

Safe local checks:

```sh
make test
make check
make charts
make benchmark-protect
```

`make check` depends on the local static-analysis toolchain; if `staticcheck`
or `actionlint` is unavailable, run the corresponding safe subset used by this
revision (`scripts/ci/check.sh fmt modtidy vet shellcheck charts`).

The full bfw/UFW container comparison and the real-attack job are intentionally
restricted to disposable GitHub-hosted runners:

```sh
# Hosted performance job only:
scripts/perf/run.sh

# Hosted attack lab only:
scripts/perf/run_attack.sh
```

The guard in `scripts/perf/run.sh` requires `CI=true`,
`GITHUB_ACTIONS=true`, and `BFW_PERF_RUNNER_ENV=github-hosted`. This is
deliberate: the harness needs `NET_ADMIN`, rewrites firewall state, and must not
run against a workstation's live firewall.
